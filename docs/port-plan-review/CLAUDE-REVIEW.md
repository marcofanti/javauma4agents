## New findings

### CL-1 · Reconcile the baseline's early cherry-picks before porting Phase A

The Java baseline is not a clean `f6e6068`: our Phase-0 work cherry-picked
mid-flight PR-#2 commits (`c3cb4e4`, parts of `a007d4e`) — family-keyed negotiations,
`/consume`, introspection reason codes, deny-by-default — whose **final** upstream form
differs after later QA and the store rework (e.g. the atomic burn now lives inside the
store contract per CX-2's evidence; `PENDING_TTL` semantics changed; dead code we
declined to port was deleted upstream). Phase A must begin with a reconciliation
inventory: for each early-ported behavior, diff our Java form against the pinned
upstream form and schedule the delta, so we don't port around stale intermediate
shapes or double-port. Proposed plan change: new Phase A work item 0.

### CL-2 · The plan has no CI, and 18–25 sessions without CI will regress

Upstream runs `check-all` = `check-unit` + `spec-check` + `check-live` as one target.
The Java repo has no CI at all. Over a multi-month port, conformance that passed in
session n silently breaks in session n+k. Proposed plan change: Phase A adds (a) a
`check-unit`-equivalent GitHub Actions workflow (`mvn test`, zero-warnings) on every
PR, and (b) Make targets `check-unit` / `check-live` / `check-all` mirroring
upstream's names, with `check-live` runnable locally against the compose stack and
required before each phase's sign-off. Compose-in-CI can stay out of scope; the local
`check-live` gate is the requirement.

### CL-3 · Record the RFC 8785 discrepancy and port the implementation, not the spec

Consequence of CX-5's evidence: the register claims RFC 8785 serialization for the
clearance digest; the implementation uses CPython `json.dumps(sort_keys=True,
separators=(",",":"), ensure_ascii=False)`. The Java port must match the
**implementation** (wire compatibility is with running code), via the existing PyJson
infrastructure, with vectors that would fail under a true JCS implementation
(e.g. a float and a non-ASCII string in the clearance object). Separately, file the
discrepancy upstream (issue on nickgamb/uma4agents) — either the draft text or the
serializer should change; the Java repo's FINDINGS entry records it until resolved.

### New findings

#### CL-4 · Vendoring must include upstream's Python client library, and the baseline already breaks byte-identity

**Evidence.**

- The pinned checks import upstream's Python library:
  - `test_shim.py` imports `uma4a_grant`
    ([L118](https://github.com/nickgamb/uma4agents/blob/7764928/clients/agent-shim/test_shim.py#L118)).
  - The `embedded`, `rotation` and `establishment` services mount `./lib` at `/driver/lib`.
- The Java repo's `lib/` holds Maven modules, so the plan's "consumed as-is" has no
  Python library to consume.
- The Java baseline's
  [`test_shim.py`](../../clients/agent-shim/test_shim.py) differs from upstream
  `f6e6068`. It adds `SHIM_CMD` and drops the `PYTHONPATH=lib` line. The claim at plan
  L13–15 and L64 is therefore already untrue.

**Proposed plan change.** Add a vendored tree under `conformance/upstream/`, containing:

- the check scripts;
- upstream's `lib/*.py` client modules;
- `clients/ts-agent`;
- a manifest of upstream path and blob hash.

Compose mounts that tree where upstream mounts `./lib` and `./clients/demo-driver`. The
pinned `test_shim.py` reads `UMA4A_REPO`
([L31](https://github.com/nickgamb/uma4agents/blob/7764928/clients/agent-shim/test_shim.py#L31)),
so the launcher points `UMA4A_REPO` at a tree containing three things:

- `clients/agent-shim/shim.py`: a stub that calls `os.execvp` on the Java jar, so the
  child process *is* Java;
- the vendored `lib/`;
- `certs/rootCA.pem`.

The current `SHIM_CMD` edit is reverted in A.

#### CL-5 · Phase A's pinned checks depend on configuration from later phases, and `fixture` depends on B

**Evidence.**

- **Portal client ID.** Every Phase A check authenticates Alice with client ID
  `meridian-portal`: `test_shim` L45, `embedded_check` L75, `check.ts` L32 and
  `driver.py` L304. The AS admits only `UMA_AS_OWNER_CLIENTS` (default
  `meridian-portal`,
  [app.py L141–142](https://github.com/nickgamb/uma4agents/blob/7764928/services/uma-as/app.py#L141-L142)).
  The rename came from #20 (`1aae472`, multi-owner, which is E). The Java realm still
  has `alice-portal`.
- **Embedded admission.** `embedded_check` admits the vault without the E1 decision
  endpoint only through its "provisioned under a name" branch
  ([L110–118](https://github.com/nickgamb/uma4agents/blob/7764928/clients/demo-driver/embedded_check.py#L110-L118)).
  That branch needs an active registry entry whose `resource_uri` starts with
  `https://gateway.uma.lab`. The Java declarative entry
  ([AsState.java L69–73](../../services/uma-as/src/main/java/io/uma4agents/authserver/AsState.java))
  has that shape.
- **Fixture.** `compose.fixture.yml` provisions the resource server, with
  `UMA_AS_RS_CLIENT_ID` and its secret, so it needs no admission. It does need
  `UMA_AS_OWNER_AUTH=local-key`, which arrived in #8 (`a00ef1f`, the owner credential in
  the flow work).

**Proposed plan change.**

- Phase A item 0 copies `keycloak/alice-realm.json` at the pin and adopts
  `UMA_AS_OWNER_CLIENTS`. Under ground rule 5, realms are copied, not ported.
- An A acceptance assertion pins the provisioned-entry shape.
- `fixture` moves to B with local-key owner auth.

**Not material, recorded for completeness.** Upstream pins person-server `4e05247` and
the Java repo pins `18d9558`. The only difference between them is the LICENSE file, so
the Java pin stays.
